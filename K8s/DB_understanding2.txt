What happened?

Your MongoDB Pod was recreated and Kubernetes scheduled the new Pod on k8s-node2:

MongoDB Pod
     │
     │ scheduled on
     ▼
k8s-node2
     │
     │ needs mongodb-pvc
     ▼
mongodb-pvc
     │
     ▼
PV
     │
     ▼
Azure Managed Disk

The important point is:

The data does not belong to the Pod or to node2. The data belongs to the Azure Managed Disk.

Why could node2 mount it?

Your PVC uses:

storageClassName: standard

and that StorageClass uses:

provisioner: disk.csi.azure.com

Therefore Kubernetes dynamically created an Azure Managed Disk.

Your PV contains:

csi:
  driver: disk.csi.azure.com
  volumeHandle: /subscriptions/.../Microsoft.Compute/disks/pvc-fb0d8e4f...

That volumeHandle is effectively the identity of the actual Azure Managed Disk.

So when MongoDB was running on another node, the disk was attached there.

When the Pod was recreated and scheduled on node2, Kubernetes/CSI handled the storage attachment for node2.

Conceptually:

Before Pod recreation

MongoDB Pod
    │
    ▼
Node ?
    │
    ▼
Azure Managed Disk
    │
    ▼
MongoDB data

After recreation:

                 Azure Managed Disk
                 ┌─────────────────┐
                 │ Test Robot      │
                 │ price: 100      │
                 └────────┬────────┘
                          │
                     CSI Driver
                          │
                          ▼
                      k8s-node2
                          │
                          ▼
                    MongoDB Pod
                          │
                          ▼
                       /data/db
The key Kubernetes process

When the new MongoDB Pod was scheduled:

Scheduler selected k8s-node2.
Kubernetes saw that the Pod requires mongodb-pvc.
PVC is bound to the existing PV.
PV identifies the Azure Disk through volumeHandle.
Azure Disk CSI Driver handles the disk attachment/mount operation.
The disk becomes available to k8s-node2.

CSI mounts the filesystem into the MongoDB container at:

/data/db
MongoDB sees the existing files.

Therefore:

Test Robot

was still present.

Why the data wasn't lost

If MongoDB's data had been stored only inside the Pod:

Pod → local filesystem

deleting the Pod would have lost the data.

But your architecture is:

Pod
 ↓
PVC
 ↓
PV
 ↓
Azure Managed Disk

So:

Pod can disappear → Pod can move to another node → Azure Disk remains → data remains.

One important limitation

Your Azure Disk is:

ReadWriteOnce (RWO)

That means the disk is generally intended to be mounted read-write by one node at a time.

It does not mean:

"This disk belongs permanently to node2."

It means:

"Kubernetes can attach this persistent disk to the node where the workload is running, subject to Azure Disk/CSI attachment rules."

That is exactly why your Pod could be recreated on node2 and still see the same MongoDB data.

This is the fundamental difference between Pod storage and persistent storage in Kubernetes.

In your case there are two separate mechanisms.

1. Label/topology tells Kubernetes about the node

Your nodes have:

topology.disk.csi.azure.com/zone=centralindia-1

Your dynamically created PV also has:

nodeAffinity:
  required:
    nodeSelectorTerms:
    - matchExpressions:
      - key: topology.disk.csi.azure.com/zone
        operator: In
        values:
        - centralindia-1

This means:

"This PV can be used on a node having this topology."

So the label is mainly used for scheduling/topology decisions.

2. CSI Driver actually performs the attach/mount

Once Kubernetes schedules your MongoDB Pod on k8s-node2:

Pod
 │
 ▼
k8s-node2
 │
 │ PVC required
 ▼
mongodb-pvc
 │
 ▼
PV
 │
 │ volumeHandle
 ▼
Azure Managed Disk

The Azure Disk CSI Driver then performs the actual storage operations.

There are two important CSI components:

Azure Disk CSI Controller
        │
        │ Attach disk to node
        ▼
   Azure Managed Disk
        │
        ▼
     k8s-node2
        │
        │ Mount disk
        ▼
   /var/lib/kubelet/...
        │
        ▼
   MongoDB container
        │
        ▼
      /data/db

So:

Node label/topology → helps determine whether the node is suitable.
PV nodeAffinity → restricts where the PV can be used.
CSI Controller → coordinates Azure disk attachment.
CSI Node plugin on node2 → performs the node-side mount.
Kubernetes volumeMount → exposes that mounted volume inside the container as /data/db.
In your specific case

Your PV has:

volumeHandle: /subscriptions/.../Microsoft.Compute/disks/pvc-fb0d8e4f...

So Kubernetes/CSI knows which Azure disk it needs.

And node2 has:

topology.disk.csi.azure.com/zone=centralindia-1

while the PV requires:

centralindia-1

Therefore node2 satisfies the PV's topology requirement.

But the actual physical attachment is not done by the label.
