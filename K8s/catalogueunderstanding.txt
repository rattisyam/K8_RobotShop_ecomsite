2. Why Deployment?

Catalogue is an application/microservice, not a database.

It does not need its own persistent storage.

A Deployment gives us:

Replica management
Automatic Pod recreation
Rolling updates
Easy scaling
Versioned ReplicaSets
Stateless application management

3. Why Service?

The Catalogue Pod needs to be accessed by other Robot Shop microservices.

Pod IPs are not stable, so we don't want other applications connecting directly to a Pod IP.

5. What we DON'T need for Catalogue

We don't need:

❌ StatefulSet
❌ PVC
❌ PV
❌ volumeClaimTemplates

because Catalogue itself doesn't need persistent disk.

3. One important thing to understand

Notice that Catalogue has:

env:
  - name: INSTANA_AGENT_HOST
    valueFrom:
      fieldRef:
        fieldPath: status.hostIP

This is interesting Kubernetes functionality.

We're saying:

"Take the IP address of the Kubernetes node hosting this Pod and inject it into the container as INSTANA_AGENT_HOST."

Conceptually:

Kubernetes Node
10.0.1.5
     │
     │ Pod scheduled here
     ▼
Catalogue Pod
     │
     │ status.hostIP
     ▼
INSTANA_AGENT_HOST=10.0.1.5

This is called the Downward API.

For our initial deployment, we can keep it exactly as the Helm chart has it.

4. Very important: Catalogue → MongoDB

Look carefully at this Deployment.

There is no MongoDB environment variable here.

That might initially look strange because Catalogue needs MongoDB.

But this tells us something important:

The application may have its MongoDB connection configured internally/defaulted rather than through environment variables in this Deployment.

So don't add random MongoDB environment variables yet.

We'll verify how the actual Robot Shop Catalogue image connects to MongoDB before changing anything.
