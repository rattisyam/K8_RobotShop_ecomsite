2. Why Deployment?

Catalogue is an application/microservice, not a database.

It does not need its own persistent storage.

A Deployment gives us:

Replica management
Automatic Pod recreation
Rolling updates
Easy scaling
Versioned ReplicaSets
Stateless application management

3. Why Service?

The Catalogue Pod needs to be accessed by other Robot Shop microservices.

Pod IPs are not stable, so we don't want other applications connecting directly to a Pod IP.

3. One important thing to understand

Notice that Catalogue has:

env:
  - name: INSTANA_AGENT_HOST
    valueFrom:
      fieldRef:
        fieldPath: status.hostIP

This is interesting Kubernetes functionality.

We're saying:

"Take the IP address of the Kubernetes node hosting this Pod and inject it into the container as INSTANA_AGENT_HOST."

Conceptually:

Kubernetes Node
10.0.1.5
     │
     │ Pod scheduled here
     ▼
Catalogue Pod
     │
     │ status.hostIP
     ▼
INSTANA_AGENT_HOST=10.0.1.5

This is called the Downward API.

For our initial deployment, we can keep it exactly as the Helm chart has it.

4. Very important: Catalogue → MongoDB

One important Kubernetes concept you've just demonstrated

The Catalogue Pod IP is:

192.168.36.87

Don't configure another application to permanently use this IP.

Instead, applications use:

catalogue:8080

Kubernetes DNS resolves catalogue to the Service:

catalogue
   ↓
10.96.3.123
   ↓
192.168.36.87:8080

If the Catalogue Pod is deleted and recreated with a different Pod IP, Kubernetes automatically updates the EndpointSlice.

That's one of the main reasons we use Services.

3. This is why Service creation order matters here

This is an interesting detail of Kubernetes.

Your Catalogue Pod was created after the MongoDB and Redis Services existed.

Therefore those Service environment variables were available when the Pod started.

But modern Kubernetes applications generally prefer DNS-based service discovery:

mongodb:27017
redis:6379
catalogue:8080

rather than relying on Service environment variables.

Why?

Because the Service IP can change if the Service itself is recreated, whereas the Service DNS name remains stable.

What happened internally

When Catalogue runs:

getent hosts mongodb

the request goes roughly like this:

Catalogue Pod
     │
     │ DNS query: mongodb
     ▼
┌──────────────────────┐
│ CoreDNS              │
│ kube-system          │
└──────────┬───────────┘
           │
           │ Service lookup
           ▼
┌──────────────────────┐
│ mongodb Service      │
│ ClusterIP            │
│ 10.104.73.58         │
└──────────┬───────────┘
           │
           ▼
       MongoDB Pod

The full Kubernetes DNS name is:

mongodb.robot-shop.svc.cluster.local

But because Catalogue and MongoDB are in the same namespace, the application can simply use:

mongodb

So these are progressively more explicit:

mongodb
mongodb.robot-shop
mongodb.robot-shop.svc
mongodb.robot-shop.svc.cluster.local

For normal application configuration, mongodb:27017 is usually sufficient.
