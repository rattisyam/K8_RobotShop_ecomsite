The open-source Azure Disk CSI driver supports Kubernetes 1.21+ and the CSI driver name is disk.csi.azure.com. It also supports ReadWriteOnce, which is exactly what we need for a single MongoDB instance.

However, there is one important issue: we should not immediately use the master's managed identity just
 because it exists. The Azure Disk CSI controller needs an Azure identity with appropriate permissions 
 to create/manage disks. The current driver documentation recommends the identity used by the driver
  have appropriate permissions on the resource group where managed disks are stored.

For your learning lab, I'd use a User Assigned Managed Identity + Workload Identity rather than embedding a service-principal secret. The Azure Disk CSI project explicitly supports workload identity on self-managed clusters.

STEP 1 — Create a User Assigned Managed Identity

We will create a dedicated identity for Azure Disk CSI.

Why?

The CSI driver needs to talk to Azure and create/manage disks.

Instead of putting an Azure username/password/client secret into Kubernetes, we'll use a Managed Identity.

Create it from your DevOps Agent:

az identity create \
  --name azuredisk-csi \
  --resource-group Azure_K8_RG \
  --location centralindia



Verify
az identity show \
  --name azuredisk-csi \
  --resource-group Azure_K8_RG \
  -o table

You should see information including:

ClientId
PrincipalId
TenantId

Get them individually:

export UAMI_CLIENT_ID=$(az identity show \
  --name azuredisk-csi \
  --resource-group Azure_K8_RG \
  --query clientId -o tsv)
export UAMI_PRINCIPAL_ID=$(az identity show \
  --name azuredisk-csi \
  --resource-group Azure_K8_RG \
  --query principalId -o tsv)
export TENANT_ID=$(az identity show \
  --name azuredisk-csi \
  --resource-group Azure_K8_RG \
  --query tenantId -o tsv)

Check:

echo $UAMI_CLIENT_ID
echo $UAMI_PRINCIPAL_ID
echo $TENANT_ID
Remember the difference
Client ID       → identifies the identity to applications
Principal ID    → Azure AD service principal/object identity
Tenant ID       → your Entra ID tenant

STEP 4 — Prepare Azure cloud configuration

This is the part that is different from local storage.

The Azure Disk CSI driver needs Azure cloud configuration when installed manually on a self-managed cluster. The driver's documentation explicitly lists the cloud-provider configuration as a prerequisite.

We will create an azure.json configuration using the UAMI.

First, create a temporary directory on the master:

ssh azureuser@10.0.1.4

Then:

sudo mkdir -p /etc/kubernetes/azure

Create the configuration:

sudo nano /etc/kubernetes/azure/azure.json

Put:

{
  "cloud": "AzurePublicCloud",
  "tenantId": "7ad7c32f-c2c7-4953-afa4-c484be33ecaf",
  "subscriptionId": "f28577aa-ecad-4b8d-a9b7-ee289e3a749c",
  "resourceGroup": "Azure_K8_RG",
  "location": "centralindia",
  "vmType": "standard",
  "useManagedIdentityExtension": true,
  "userAssignedIdentityID": "YOUR_UAMI_CLIENT_ID",
  "useInstanceMetadata": true
}

Replace:

YOUR_UAMI_CLIENT_ID

with the value from:

echo $UAMI_CLIENT_ID
Why?

This tells the Azure cloud provider:

Which Azure cloud?        AzurePublicCloud
Which tenant?             your tenant
Which subscription?      your subscription
Which resource group?    Azure_K8_RG
Which region?            centralindia
How authenticate?        Managed Identity
Which identity?          azuredisk-csi

The cloud-provider Azure configuration supports managed identity settings such as useManagedIdentityExtension and userAssignedIdentityID.

STEP 5 — Make the configuration available to CSI

We don't want to simply put a random file inside one Pod.

We'll create a Kubernetes Secret/ConfigMap containing the cloud configuration so the CSI driver can consume it.

The Azure Disk CSI documentation supports providing the cloud-provider configuration through Kubernetes configuration.

From the master:

kubectl create secret generic azure-cloud-provider \
  --namespace kube-system \
  --from-file=azure.json=/etc/kubernetes/azure/azure.json

Verify:

kubectl get secret azure-cloud-provider -n kube-system

You should see:

azure-cloud-provider
Why Secret?

Because Azure cloud configuration can contain sensitive credentials in some authentication models.

In our case we're using Managed Identity, so we don't have a client secret, but keeping the cloud configuration in a Kubernetes Secret is still appropriate.

et me summarize the actual problem, why it happened, and exactly how we fixed it in simple terms.

1. What were we trying to achieve?

We installed the Azure Disk CSI Driver so that Kubernetes can do this:

Kubernetes PVC
      ↓
Azure Disk CSI Driver
      ↓
Azure Managed Disk
      ↓
PV
      ↓
Pod mounts the disk

For that to work, every Kubernetes node needs a healthy Azure Disk CSI node plugin.

Your cluster has:

k8s-master   10.0.1.4
k8s-node1    10.0.1.5
k8s-node2    10.0.1.6

Eventually we wanted:

Master   → Azure Disk CSI ✅
Node1    → Azure Disk CSI ✅
Node2    → Azure Disk CSI ✅

And we now have exactly that.

2. What was the first problem?

Initially the CSI driver couldn't get Azure cloud configuration.

The important log was:

InitializeCloudFromSecret:
failed to get cloud config from secret
no data in secret

Then it tried the fallback:

/etc/kubernetes/azure.json

But that file didn't exist:

open /etc/kubernetes/azure.json:
no such file or directory

So the CSI driver said:

no cloud config provided
driver will run without cloud config

And consequently:

no credentials provided for Azure cloud provider
In simple words

The CSI driver was basically saying:

"I need Azure information so I can talk to Azure, but I don't have the configuration."

3. Why did this happen?

Your Helm deployment was configured to use:

Secret: azure-cloud-provider
Namespace: kube-system

But the Secret originally contained:

azure.json

The CSI driver version/chart we were using expected the cloud configuration through the appropriate Secret data entry.

We added:

cloud-config

while keeping the existing azure.json.

So the Secret became:

azure-cloud-provider
├── azure.json
└── cloud-config

After that, the logs changed dramatically.

Instead of:

no credentials provided

we saw:

Setting up ARM client factory for network resources
Setting up ARM client factory for compute resources

and then:

NodeGetInfo
failureDomain: centralindia-1
VM Size: STANDARD_B2S
MaxDataDiskCount: 4
This proved:

Azure authentication was fixed.

The CSI driver could now communicate with Azure.

4. Then we encountered the second problem

After Azure authentication was fixed, the CSI driver discovered the Azure zone:

centralindia-1

But Kubernetes already had an empty label on the nodes:

topology.disk.csi.azure.com/zone=

So the CSI driver wanted to say:

topology.disk.csi.azure.com/zone=centralindia-1

but Kubernetes effectively said:

"That label already exists, and its value is empty."

Therefore the node-driver-registrar reported:

detected topology value collision

Specifically:

driver reported:
centralindia-1

existing label:
""
5. Why did this cause the CSI pod to fail?

The CSI node driver doesn't just run the container.

It also has to register itself with Kubernetes.

The process is approximately:

Azure Disk CSI container
        ↓
node-driver-registrar
        ↓
Kubernetes Node
        ↓
CSINode object

The registrar tried to register:

disk.csi.azure.com

with topology:

centralindia-1

But the existing empty label caused a collision.

So the registrar failed:

RegisterPlugin error

and restarted.

That's why we saw:

2/3 CrashLoopBackOff

The two healthy containers were:

azuredisk
liveness-probe

while:

node-driver-registrar

was repeatedly crashing.

6. Why did node1 and node2 eventually work?

We found this stale label on the nodes:

topology.disk.csi.azure.com/zone=

We removed it with:

kubectl label node k8s-node1 topology.disk.csi.azure.com/zone-

and:

kubectl label node k8s-node2 topology.disk.csi.azure.com/zone-

Then the CSI registrar was able to register successfully.

The result became:

topology.disk.csi.azure.com/zone=centralindia-1

And the CSINode objects showed:

disk.csi.azure.com

with:

allocatable count: 4
